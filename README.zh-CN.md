### 🌐 从孤立助手走向持续进化的实验室

多数 Agent 系统停留在一次对话或临时组建的 Agent 小组。真实工作需要更多能力：人能够招募专业成员，把人的判断与 Agent 的执行结合起来，在长任务中保留明确责任，评估结果，并持续改进产出这些结果的实验室。

### 💡 Janus 的方案

**Janus 是一个用于建立和运营持续进化 Agent 实验室的桌面工作空间。** 人与 Agent 在持久化工作流中协作；每个 Agent 都有可见的角色、绩效与领导力记录，以及受治理的能力版本历史。

## ✨ 核心功能

1. **人与 Agent 协作** —— 连接人、uBuddy 与 Agent，支持共享任务群、直接沟通和跨用户委托。

2. **持久化任务编排** —— 将目标转化为直接执行、专业 Agent 委派或带依赖关系的多 Agent 工作流，持续保留上下文与验收状态。

3. **受治理的 Agent 进化** —— 通过审核、评估、受控发布、采用与回滚，改进个体 Agent 和可复用的集群能力。

4. **可见的人才生命周期** —— 将招募、角色、绩效、领导力和 Skill/Memory 版本作为独立且可审计的机制跟踪。

5. **以交付物为中心的工作区** —— 在用户选择的项目中工作，返回可验收的研究、项目变更和可编辑产物。

## 🔮 uBuddy

uBuddy 在保留高价值真人协作的同时，减少重复、低信息密度的协调。它直接解决 **One-to-N 协作问题**：一个目标可以在多个用户与 Agent 之间被结构化、委托、跟踪和汇总，只在需要真人判断时介入。

| 🧭 能力 | ⚙️ 动作 | ⚡ 结果 |
| --- | --- | --- |
| **任务简报** | 整理目标、文件、约束与验收标准。 | 形成一份明确简报。 |
| **One-to-N 编排** | 委托、分工、排序并汇总。 | 实现多方协同交付。 |
| **决策升级** | 处理进度、交接与可恢复问题。 | 仅为关键决策保留真人注意力。 |

## 🧬 Agent 自进化

Janus 把 Agent 能力视为一个受治理、可追踪版本的过程，而不是一段固定提示词。进化来自真实工作证据，并与实验室内的招募、评估和责任持续关联。

| ⚙️ 机制 | 🎯 对象或产出 | 💡 目的 |
| --- | --- | --- |
| **个体进化** | 已招募的 Agent | 根据所有者的工作与反馈调整 Skill 和 Memory。 |
| **集群进化** | 符合条件的活跃 Agent 集群 | 从共享工作证据中提炼兼顾隐私的可复用改进。 |
| **人才市场** | 已批准的集群产出 | 验证并发布可采用或回滚的版本。 |

## 📜 Agent 治理

Janus 将三类机制相互连接，但不会将它们视为同一条自动流水线：

| 🧭 层级 | 🎯 责任 | ⚙️ 操作 |
| --- | --- | --- |
| **Agent 员工生命周期** | 实验室与 Agent 的任职关系 | 招募、任用、停用、重新启用或解除任用。 |
| **绩效与领导力** | 准备度、贡献与责任 | 考核、晋升、设定领导力等级并执行治理决策。 |
| **能力进化** | 受治理的 Skill 与 Memory 版本 | 进化、审核、激活、监测、采用或回滚。 |

## 🚀 快速开始

可前往 [GitHub Releases](https://github.com/iLearn-Agent/Janus/releases) 下载对应操作系统的版本。

Janus 安装后即可开箱使用，每位用户每天均可获得免费 Token 额度。如需使用自定义模型服务，请参考下方配置指南。

### 🍎 在 macOS 上启动

当前 macOS 构建尚未签名或公证。将 `Janus.app` 移动到 `/Applications` 后，在终端运行以下命令启动：

```bash
xattr -cr /Applications/Janus.app
codesign --force --deep --sign - /Applications/Janus.app
open /Applications/Janus.app
```

### ⚙️ 在 Janus 软件中配置

1. 打开 **设置 → 账户与权限 → 模型服务**。
2. 填写 Provider 的 API URL，通常以 `/v1` 结尾。
3. 填写 API Key。
4. 点击 **保存并测试**。Janus 会检查连接，并加载 Provider 实际提供的模型与推理选项。

Provider 需要兼容当前 backbone 的 Responses API 合约。如果当前默认模型不在 Provider 的模型目录中，请从刷新后的模型菜单中选择可用模型。

### 📁 通过本地文件配置

开发环境配置文件：

```text
workspace/config/codex/config.toml
workspace/config/codex/auth.json
```

安装后的应用在 Janus 用户目录中使用相同的 `config/codex` 结构。常见位置：

```text
Windows: %USERPROFILE%\.janus\config\codex\
macOS:   ~/.janus/config/codex/
Linux:   ~/.janus/config/codex/
```

可以从自动生成的 `config.toml.template` 开始。通常只需要替换 `base_url`；只有 Provider 使用不同模型 ID 时才需要修改已有模型字段。

修改 `config.toml` 中当前使用的 Provider 配置块：

```toml
[model_providers.custom]
name = "custom"
base_url = "https://provider.example.com/v1"
wire_api = "responses"
requires_openai_auth = true
env_key = "OPENAI_API_KEY"
request_max_retries = 4
stream_max_retries = 5
```

`auth.json`：

```json
{
  "OPENAI_API_KEY": "your-api-key"
}
```

保存两个文件后，返回 **模型服务** 运行连接测试。凭据会保存在当前桌面配置中。

## 🌍 自建服务

共享账号、实验室工作区、消息、跨用户委托、同步协作、共享文件和共享进化服务需要部署自建服务。支持的 Community 部署通过 Docker Compose 运行 PostgreSQL、MinIO、Migrator、Cloud API、隔离的 Evolution Worker 和 Caddy。

部署者需要准备安装 Docker Compose 的 Linux 主机、公网域名、SMTP 邮件发送、备份和私密服务凭据。运行时数据库、对象数据、用户记录和生产密钥不包含在本仓库中，也绝不能提交到 Git。
