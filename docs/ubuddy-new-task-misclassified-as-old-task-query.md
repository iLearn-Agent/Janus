# uBuddy 新任务错误返回旧任务结果：根因分析

日期：2026-08-06

## 问题现象

用户先让 uBuddy 完成了一个任务，随后发送了一个内容完全不同的新任务，例如：

> 请在当前项目根目录创建 `review-ui-demo.md`，写入一个标题、三个小节和至少 30 行测试内容。完成后告诉我文件路径。

界面没有展示新任务的执行过程或结果，而是再次返回了旧任务“1”的完成状态及旧产物路径。

从用户视角看，表现为“uBuddy 一直提醒前一个任务已经完成，不显示新任务结果”。

## 实际根因

问题不在任务持久化，也不是旧任务结果覆盖了新任务结果。真正原因是：**新任务在进入任务创建流程之前，被意图识别规则错误地判定成了旧任务产物查询。**

相关判断位于：

- `src/main/modules/collaboration/application/secretaryTaskQuery.js`
- `src/main/runtime.js`

原有规则会检查消息中是否包含类似以下表达：

- “文件路径在哪里”
- “产物保存到哪”
- “告诉我文档位置”

用户的新任务末尾包含：

> 完成后告诉我文件路径。

因此消息命中了 `artifact`（查询任务产物）意图。运行时随后执行了以下错误流程：

1. 将整条新指令识别为“查询产物”。
2. 跳过新任务的检查、规划和创建流程。
3. 从当前 uBuddy 会话中选择最近一个已有任务。
4. 最近任务恰好是已经完成的任务“1”。
5. 调用 `buildSecretaryTaskQueryReply()` 生成旧任务状态和旧产物路径。
6. 用户看到旧任务再次完成，误以为新任务结果被旧结果覆盖。

简化调用链如下：

```text
用户发送新的文件创建任务
        ↓
classifySecretaryTaskQuery()
        ↓
末尾“告诉我文件路径”命中 artifact 查询
        ↓
selectSecretaryTaskQueryCandidates()
        ↓
选择最近的旧任务“1”
        ↓
buildSecretaryTaskQueryReply()
        ↓
返回旧任务状态和旧产物路径
```

## 为什么第一次修复没有解决

第一次排查发现渲染器存在异步消息刷新竞态：多个消息列表请求可能乱序返回，较旧的请求有机会覆盖较新的界面状态。

这个竞态确实存在，因此增加了按会话递增的请求版本保护，旧请求现在不会覆盖新请求。但是截图中的复现并不是该竞态造成的：

- 新用户消息已经正确保存并显示。
- 服务端主动生成了一条旧任务查询回复。
- 新任务从一开始就没有进入创建流程。

所以第一次修复解决的是“旧页面快照覆盖新页面快照”，但本次截图暴露的是更早一层的“新任务被误判为旧任务查询”。两者现象相似，根因不同。

## 最终修复

修复调整了工作指令与查询指令的判断优先级。

当消息明确包含创建或执行动作时，即使末尾要求返回文件路径，也必须优先视为工作请求，而不是产物查询。当前覆盖的动作包括：

- 生成、制作、创建、新建
- 编写、写入、撰写
- 修改、修复、实现、开发、重做
- 执行、运行、构建、部署、安装、整理、导出

同时支持带位置前缀的命令，例如：

```text
请在当前项目根目录创建……
在这个目录下新建……
请于工作区内编写……
```

真正的查询仍保持原行为，例如：

```text
请告诉我生成的文档在哪里。
这个任务完成了吗？
当前任务进度怎么样？
```

## 回归测试

已增加与用户原始输入一致的测试，确认以下指令不会再被识别为旧任务查询：

```text
请在当前项目根目录创建 review-ui-demo.md，写入一个标题、三个小节和至少 30 行测试内容。完成后告诉我文件路径。
```

同时增加了以下边界测试：

```text
请在当前项目根目录下，新建一个测试文档，完成后告诉我保存位置。
```

并确认真正的查询仍然会被正确识别：

```text
请在当前项目里告诉我生成的文档在哪里。
```

## 与截图中 Codex CLI 超时的关系

截图上方还出现了 `Codex CLI could not be launched` 和进程超时信息。这是任务检查阶段启动 Codex CLI 失败，属于独立的运行环境或进程启动问题。

它和“新任务返回旧任务结果”的意图误判不是同一个根因：

- CLI 超时会导致任务检查或执行失败。
- 意图误判会导致新任务根本不被创建，直接查询旧任务。

本次修改解决的是第二项。若新包中仍出现 CLI 启动超时，需要单独收集该次运行日志继续排查。

## 结论

本问题的核心不是 uBuddy 重复发送旧任务通知，而是自然语言规则把“创建文件，完成后告诉我路径”错误理解成了“查询已有文件路径”。修复后，明确的创建和执行动作会优先进入新任务流程，末尾的路径交付要求只作为任务要求保留，不再触发旧任务查询。
